S Single Responsibility Principle

▼

Definition: "A class should have only one reason to change." — Robert C. Martin

In practice: every class, function, or module should focus on a single concern. This makes code easier to understand, test, and modify.

❌ Violation: A User class that handles authentication, profile management, email sending, and database persistence — it has many reasons to change.
❌ BAD — violates SRP
// This class does TOO many things
public class User {
    private String name;
    private String email;

    // Reason 1: User data validation
    public boolean validateEmail() {
        return email.contains("@");
    }

    // Reason 2: Database persistence
    public void saveToDatabase() {
        // SQL logic here
        System.out.println("INSERT INTO users...");
    }

    // Reason 3: Email notification
    public void sendWelcomeEmail() {
        // SMTP logic here
        System.out.println("Sending email to: " + email);
    }

    // Reason 4: Report generation
    public String generateReport() {
        return "User Report: " + name;
    }
}
✅ GOOD — follows SRP
// Each class has one clear responsibility

public class User {                          // Holds user data only
    private String name;
    private String email;
    public String getName()  { return name;  }
    public String getEmail() { return email; }
}

public class UserValidator {               // Validation logic
    public boolean isValidEmail(User user) {
        return user.getEmail().contains("@");
    }
}

public class UserRepository {             // DB persistence
    public void save(User user) {
        // SQL INSERT logic
    }
    public User findById(int id) { return null; }
}

public class EmailService {               // Email sending
    public void sendWelcome(User user) {
        // SMTP logic
    }
}

public class UserReportGenerator {         // Report generation
    public String generate(User user) {
        return "User Report: " + user.getName();
    }
}
✅ Industry Context: In microservices, SRP maps directly to service boundaries. Each service (UserService, NotificationService, ReportingService) has a single business capability. Spring Boot services naturally enforce SRP through @Service, @Repository, @Component separation.

O Open/Closed Principle

▼

Definition: Software entities should be open for extension but closed for modification.

Achieve this using abstractions (interfaces/abstract classes) so new behavior can be added by creating new classes rather than modifying existing ones.

❌ Violation: Every time you add a new payment method to a PaymentProcessor, you modify the existing switch/if chain — breaking OCP.
// ❌ BAD: Must modify this class every time new payment type is added
public class PaymentProcessor {
    public void processPayment(String type, double amount) {
        if (type.equals("CREDIT_CARD")) {
            System.out.println("Processing credit card: $" + amount);
        } else if (type.equals("PAYPAL")) {
            System.out.println("Processing PayPal: $" + amount);
        } else if (type.equals("CRYPTO")) {   // Added later — forces modification!
            System.out.println("Processing Crypto: $" + amount);
        }
    }
}
// ✅ GOOD: Open for extension (new class), closed for modification

public interface PaymentMethod {
    void process(double amount);
}

public class CreditCardPayment implements PaymentMethod {
    @Override
    public void process(double amount) {
        System.out.println("Charging credit card: $" + amount);
        // Stripe/Braintree integration
    }
}

public class PayPalPayment implements PaymentMethod {
    @Override
    public void process(double amount) {
        System.out.println("PayPal transfer: $" + amount);
    }
}

// Adding Crypto? Just create a new class — no existing code changes!
public class CryptoPayment implements PaymentMethod {
    @Override
    public void process(double amount) {
        System.out.println("Bitcoin transfer: $" + amount);
    }
}

public class PaymentProcessor {
    public void processPayment(PaymentMethod method, double amount) {
        method.process(amount);   // Never needs to change
    }
}
✅ Real World: Java's Comparator interface, Spring's HandlerInterceptor, and JPA's Specification pattern all follow OCP — you extend behavior without touching framework code.

L Liskov Substitution Principle

▼

Definition: If S is a subtype of T, then objects of type T may be replaced with objects of type S without altering the correctness of the program.

In simple terms: derived classes must be fully substitutable for base classes. A subclass should honor the contract of the parent class.

❌ Classic Violation: Square extends Rectangle. Setting width on a Square secretly changes height too — breaks the Rectangle contract.
// ❌ The classic Rectangle–Square violation
public class Rectangle {
    protected int width, height;
    public void setWidth(int w)  { this.width  = w; }
    public void setHeight(int h) { this.height = h; }
    public int  area()            { return width * height; }
}

public class Square extends Rectangle {
    @Override
    public void setWidth(int w)  { this.width = this.height = w; } // 💥 Surprise!
    @Override
    public void setHeight(int h) { this.width = this.height = h; } // 💥 Surprise!
}

// Code that works for Rectangle breaks for Square!
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(10);
    // Expected area = 50, but Square gives 100 — LSP violated!
    assert r.area() == 50;
}
// ✅ GOOD: Model shapes independently using abstraction
public interface Shape {
    int area();
}

public class Rectangle implements Shape {
    private int width, height;
    public Rectangle(int w, int h) { width = w; height = h; }
    @Override public int area() { return width * height; }
}

public class Square implements Shape {
    private int side;
    public Square(int s) { side = s; }
    @Override public int area() { return side * side; }
}
// Now both are interchangeable via Shape — no surprises!
✅ Rule of thumb: If you find yourself using instanceof checks in methods that accept a base type, you're likely violating LSP. Fix by refactoring the hierarchy or using polymorphism properly.

I Interface Segregation Principle

▼

Definition: Clients should not be forced to depend on interfaces they do not use. Prefer multiple specific interfaces over one general-purpose "fat" interface.

❌ Violation: A single Worker interface with methods work(), eat(), sleep() forces Robot classes to implement eat() and sleep() with empty/error bodies.
// ❌ BAD: Fat interface forces irrelevant methods
public interface Worker {
    void work();
    void eat();    // Robots don't eat!
    void sleep();  // Robots don't sleep!
}

public class Robot implements Worker {
    @Override public void work()  { System.out.println("Working 24/7"); }
    @Override public void eat()   { throw new UnsupportedOperationException(); } // 💥
    @Override public void sleep() { throw new UnsupportedOperationException(); } // 💥
}
// ✅ GOOD: Segregated interfaces
public interface Workable  { void work();  }
public interface Eatable   { void eat();   }
public interface Sleepable { void sleep(); }

public class HumanWorker implements Workable, Eatable, Sleepable {
    @Override public void work()  { System.out.println("Human working");  }
    @Override public void eat()   { System.out.println("Human eating");   }
    @Override public void sleep() { System.out.println("Human sleeping"); }
}

public class Robot implements Workable {  // Only what it needs!
    @Override public void work() { System.out.println("Robot working 24/7"); }
}

// Industry example: Java's Serializable, Comparable, Cloneable are all segregated
// Spring's ApplicationListener<E>, InitializingBean, DisposableBean are ISP-compliant
💡 Test: If implementing an interface forces you to write throw new UnsupportedOperationException() — ISP is being violated. Break the interface up.

D Dependency Inversion Principle

▼

Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions.

// ❌ BAD: OrderService directly depends on concrete MySQLDatabase
public class MySQLDatabase {
    public void save(String data) { System.out.println("MySQL: " + data); }
}

public class OrderService {
    private MySQLDatabase db = new MySQLDatabase();  // Tightly coupled! 💥
    public void placeOrder(String order) {
        db.save(order);
    }
}
// ✅ GOOD: Both depend on the Database abstraction
public interface Database {
    void save(String data);
}

public class MySQLDatabase implements Database {
    @Override
    public void save(String data) { System.out.println("MySQL: " + data); }
}

public class MongoDatabase implements Database {
    @Override
    public void save(String data) { System.out.println("MongoDB: " + data); }
}

public class OrderService {
    private final Database db;    // Depends on abstraction!

    public OrderService(Database db) {  // Injected via constructor (Spring @Autowired)
        this.db = db;
    }

    public void placeOrder(String order) {
        db.save(order);   // Switch from MySQL to Mongo without touching this class!
    }
}

// Usage — Spring Boot does this automatically with @Autowired
Database db = new MySQLDatabase();
OrderService service = new OrderService(db);
✅ Spring Context: Spring's IoC container IS dependency inversion at scale. @Service, @Repository, @Component — you wire abstractions, Spring provides implementations at runtime. This is DIP applied to an entire framework.

Singleton Ensure only one instance — 5 Evolution Approaches

▼

Intent: Guarantee a class has exactly one instance with a global access point. Each approach below fixes the flaw of the previous one.

💡 Read in order. Each step introduces a problem the next step solves. This is exactly how interviewers walk through Singleton depth.
STEP 1 — NAIVE (Broken in multithreading)
Two threads both see instance==null simultaneously → create two instances. Race condition.
public class NaiveSingleton {
    private static NaiveSingleton instance; // not volatile — visibility problem

    private NaiveSingleton() {}

    public static NaiveSingleton getInstance() {
        if (instance == null) {           // Thread A and B both see null here
            instance = new NaiveSingleton(); // BOTH create an instance → broken
        }
        return instance;
    }
}
Problem: Not thread-safe. Two separate instances can be created.
STEP 2 — SYNCHRONIZED METHOD (Thread-safe but slow)
Add synchronized to getInstance() — only one thread enters at a time.
public class SynchronizedSingleton {
    private static SynchronizedSingleton instance;

    private SynchronizedSingleton() {}

    // synchronized ensures only one thread creates the instance
    public static synchronized SynchronizedSingleton getInstance() {
        if (instance == null) {
            instance = new SynchronizedSingleton();
        }
        return instance;
    }
}
Problem: synchronized is expensive — acquires lock on EVERY call, even after instance exists. 100x slower than unsynchronized for post-init reads.
STEP 3 — DOUBLE-CHECKED LOCKING (Fast + thread-safe, Java 5+)
Check outside lock (fast path) → check inside lock (safe path). volatile prevents instruction reordering.
public class DCLSingleton {
    // volatile: prevents CPU reordering instance = new DCLSingleton()
    // Without volatile, another thread may see a partially-constructed object!
    // new T() does: 1) alloc memory 2) init fields 3) assign ref
    // CPU can reorder to: 1) alloc 2) assign ref 3) init fields
    // → another thread reads non-null but uninitialized object
    private static volatile DCLSingleton instance;

    private DCLSingleton() {}

    public static DCLSingleton getInstance() {
        if (instance == null) {                  // 1st check: no lock (fast path)
            synchronized (DCLSingleton.class) {
                if (instance == null) {           // 2nd check: with lock (safe)
                    instance = new DCLSingleton();
                }
            }
        }
        return instance; // fast: no lock after first initialization
    }
}
// Flow: 99% of calls → first null check false → return immediately (no lock)
//       First call only → enters sync block → creates instance
Problem: Verbose. Requires volatile. Still susceptible to reflection attacks (someone calls private constructor via reflection).
STEP 4 — INITIALIZATION-ON-DEMAND HOLDER (Bill Pugh — elegant & lazy)
Rely on JVM's class loading guarantee: inner class is loaded only when getInstance() is called. JVM guarantees static initializers are thread-safe.
public class HolderSingleton {

    private HolderSingleton() {}

    // Static inner class — NOT loaded when outer class loads.
    // Loaded (and INSTANCE created) only when getInstance() is first called.
    // JVM class loading is inherently thread-safe — no synchronized needed!
    private static class Holder {
        static final HolderSingleton INSTANCE = new HolderSingleton();
    }

    public static HolderSingleton getInstance() {
        return Holder.INSTANCE; // triggers class load → creates instance once
    }
}
// Why this works:
// 1. Holder class loaded only when getInstance() first called → lazy
// 2. JVM guarantees static initializers run exactly once, atomically → safe
// 3. No synchronized, no volatile, no locks → fast
// 4. Simpler code than DCL
Problem: Still breakable via Java Serialization (deserializing creates a new instance) and via Reflection API.
STEP 5 — ENUM SINGLETON (Joshua Bloch — Java best practice, reflection/serialization-safe)
JVM guarantees enum instances are singletons by spec — immune to reflection, serialization, and cloning attacks.
// Joshua Bloch (Effective Java, Item 3): "a single-element enum type
// is often the best way to implement a singleton"
public enum AppConfig {
    INSTANCE; // JVM guarantees: one instance, ever. Cannot be reflected or deserialized.

    private String dbHost;
    private int dbPort;

    @SuppressWarnings("unused")
    AppConfig() { // private by default in enums
        dbHost = System.getenv("DB_HOST");
        dbPort = Integer.parseInt(System.getenv("DB_PORT"));
    }

    public String getDbHost() { return dbHost; }
    public int getDbPort()   { return dbPort; }
}

// Usage:
// AppConfig config = AppConfig.INSTANCE;
// config.getDbHost();
//
// Why enum is unbreakable:
// - Reflection: Constructor.newInstance() throws IllegalArgumentException for enums
// - Serialization: Enum serialization returns existing instance by name (not new object)
// - Cloning: Enum clone() is final and throws CloneNotSupportedException

Factory Method Delegate object creation to subclasses — 3 Evolution Approaches

▼

Intent: Define an interface for creating an object, but let subclasses decide which class to instantiate. Decouples creator from product.

STEP 1 — DIRECT INSTANTIATION (The Problem)
// Business logic tightly coupled to concrete classes
// Every new notification type requires modifying this class → violates OCP
public class NotificationService {
    public void sendAlert(String type, String msg) {
        if (type.equals("EMAIL")) {
            EmailNotification n = new EmailNotification(); // hard-coded
            n.send(msg);
        } else if (type.equals("SMS")) {
            SmsNotification n = new SmsNotification();    // hard-coded
            n.send(msg);
        } // Adding PUSH requires editing this class → OCP violation
    }
}
Adding a new channel requires modifying NotificationService — breaks Open/Closed Principle.
STEP 2 — SIMPLE FACTORY (centralized but still not extensible)
public interface Notification { void send(String msg); }

public class EmailNotification implements Notification {
    public void send(String msg) { System.out.println("Email: " + msg); }
}
public class SmsNotification implements Notification {
    public void send(String msg) { System.out.println("SMS: " + msg); }
}

// Simple Factory — creation centralized but still requires modification for new types
public class NotificationFactory {
    public static Notification create(String type) {
        return switch (type) {
            case "EMAIL" -> new EmailNotification();
            case "SMS"   -> new SmsNotification();
            default -> throw new IllegalArgumentException("Unknown: " + type);
        };
    }
}

Builder Construct complex objects step by step — Telescoping to Fluent

▼

Intent: Separate construction of a complex object from its representation. Same construction process can create different representations.

STEP 1 — TELESCOPING CONSTRUCTOR (The Problem)
// When an object has many optional fields, constructors proliferate:
// HttpRequest(url)
// HttpRequest(url, method)
// HttpRequest(url, method, headers)
// HttpRequest(url, method, headers, body)
// HttpRequest(url, method, headers, body, timeout)  ← unreadable

                   String body, int timeout, boolean followRedirects) {
    // Which param is which? Easy to swap timeout and followRedirects!

STEP 2 — BUILDER PATTERN (Fluent API — readable, safe, immutable)
Each setter returns the builder (fluent). build() validates and constructs the final immutable object.
public class HttpRequest {
    // All fields final → immutable after construction
    private final String url;
    private final String method;
    private final Map<String,String> headers;
    private final String body;
    private final int timeoutMs;
    private final boolean followRedirects;

    private HttpRequest(Builder b) {
        this.url             = b.url;
        this.method          = b.method;
        this.headers         = Collections.unmodifiableMap(b.headers);
        this.body            = b.body;
        this.timeoutMs       = b.timeoutMs;
        this.followRedirects = b.followRedirects;
    }

    public static class Builder {
        private final String url;           // required
        private String method = "GET";     // optional with defaults
        private Map<String,String> headers = new HashMap<>();
        private String body = null;
        private int timeoutMs = 3000;
        private boolean followRedirects = true;

        public Builder(String url) { this.url = url; } // required param in ctor

        public Builder method(String m)           { this.method = m; return this; }
        public Builder header(String k, String v) { headers.put(k,v); return this; }
        public Builder body(String b)             { this.body = b; return this; }
        public Builder timeout(int ms)            { timeoutMs = ms; return this; }
        public Builder noRedirects()              { followRedirects = false; return this; }

        public HttpRequest build() {
            if (url == null || url.isEmpty()) throw new IllegalStateException("URL required");
            if (body != null && method.equals("GET")) throw new IllegalStateException("GET cannot have body");
            return new HttpRequest(this); // immutable object
        }
    }
}

Prototype Clone objects instead of creating from scratch — Shallow vs Deep

▼

Intent: Create new objects by copying an existing object (prototype). Avoids costly initialization when a similar object already exists.

Use when: Object creation is expensive (DB query, network call, computation), you need many similar objects with slight variations, or object state must be preserved exactly.

APPROACH 1 — SHALLOW CLONE (copies references, not nested objects)
public class UserProfile implements Cloneable {
    private String name;
    private List<String> permissions; // reference — shared in shallow clone!

    @Override
    public UserProfile clone() {
        try {
            return (UserProfile) super.clone(); // shallow: copies primitive + refs
        } catch (CloneNotSupportedException e) { throw new RuntimeException(e); }
    }
}
// DANGER: clone.permissions == original.permissions (same list!)
// Modifying clone's permissions also modifies original's permissions
Shallow clone shares mutable nested objects between original and clone — modifications to one affect the other.
APPROACH 2 — DEEP CLONE (fully independent copy)
public class WorkflowTemplate implements Cloneable {
    private String name;
    private List<Step> steps;           // Step objects must also be cloned
    private Map<String,String> config;

    @Override
    public WorkflowTemplate clone() {
        try {
            WorkflowTemplate copy = (WorkflowTemplate) super.clone();
            // Deep copy mutable fields:
            copy.steps  = steps.stream()
                              .map(Step::clone)      // each Step must also be cloneable
                              .collect(Collectors.toList());
            copy.config = new HashMap<>(config);   // new map, same String refs (OK: immutable)
            return copy;
        } catch (CloneNotSupportedException e) { throw new RuntimeException(e); }
    }
}
// Prototype Registry — cache expensive prototypes, clone on demand:
public class TemplateRegistry {
    private Map<String, WorkflowTemplate> templates = new HashMap<>();
    public void register(String key, WorkflowTemplate t) { templates.put(key, t); }
    public WorkflowTemplate get(String key) { return templates.get(key).clone(); }
    // Usage: registry.get("onboarding") → fresh copy ready to customize
}

Decorator Add behaviour dynamically at runtime — Stacking Wrappers

▼

Intent: Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

Key insight: Each decorator implements the same interface AND holds a reference to another object of that interface — enabling unlimited stacking without combinatorial explosion of subclasses.

Decorator Stacking (like Russian dolls): Client → LoggingDecorator wraps CachingDecorator wraps RetryDecorator wraps HttpDataService (real impl) Call flows through each wrapper in order — each adds its concern
public interface DataService {
    String fetchData(String key);
}

// Core implementation
public class HttpDataService implements DataService {
    public String fetchData(String key) {
        return HttpClient.get("https://api.example.com/data/" + key); // real HTTP call
    }
}

// Abstract base decorator — holds reference to wrapped service
public abstract class DataServiceDecorator implements DataService {
    protected final DataService wrapped;
    public DataServiceDecorator(DataService wrapped) { this.wrapped = wrapped; }
}

// Decorator 1: Caching
public class CachingDecorator extends DataServiceDecorator {
    private final Map<String,String> cache = new ConcurrentHashMap<>();
    public CachingDecorator(DataService s) { super(s); }

    public String fetchData(String key) {
        return cache.computeIfAbsent(key, k -> wrapped.fetchData(k)); // cache-aside
    }
}

// Decorator 2: Retry
public class RetryDecorator extends DataServiceDecorator {
    private final int maxRetries;
    public RetryDecorator(DataService s, int maxRetries) { super(s); this.maxRetries = maxRetries; }

    public String fetchData(String key) {
        for (int attempt = 1; attempt <= maxRetries; attempt++) {
            try { return wrapped.fetchData(key); }
            catch (Exception e) {
                if (attempt == maxRetries) throw e;
                Thread.sleep(100L * attempt); // exponential backoff
            }
        }
        throw new RuntimeException("All retries exhausted");
    }
}

// Decorator 3: Logging
public class LoggingDecorator extends DataServiceDecorator {
    public LoggingDecorator(DataService s) { super(s); }
    public String fetchData(String key) {
        long start = System.currentTimeMillis();
        String result = wrapped.fetchData(key);
        System.out.printf("fetchData(%s) took %dms%n", key, System.currentTimeMillis()-start);
        return result;
    }
}

// Compose at runtime — order matters!
DataService service =
    new LoggingDecorator(           // outermost: logs timing
      new CachingDecorator(           // middle: check cache first
        new RetryDecorator(            // inner: retry on failure
          new HttpDataService(), 3))); // real impl: HTTP call

// Without Decorator: 3 concerns × N implementations = 3N subclasses
// With Decorator: 3 decorators + N implementations, mix freely at runtime

Facade Simplify a complex subsystem behind a clean API

▼

Intent: Provide a simplified interface to a complex subsystem. Doesn't prevent direct access — just makes common operations easier.

public class OrderFacade {
    private final InventoryService    inventory;
    private final PricingService      pricing;
    private final PaymentService      payment;
    private final ShippingService     shipping;
    private final NotificationService notifier;
    private final AuditService        audit;

    public OrderResult placeOrder(Cart cart, Customer customer) {
        // 1. Check inventory
        if (!inventory.checkAvailability(cart.getItems()))
            return OrderResult.failure("Items out of stock");

        // 2. Calculate final price (discounts, taxes, promotions)
        Price finalPrice = pricing.calculateTotal(cart, customer.getSegment());

        // 3. Process payment
        Transaction tx = payment.charge(customer.getPaymentMethod(), finalPrice);
        if (!tx.isSuccessful()) return OrderResult.failure("Payment declined");

        // 4. Reserve inventory
        inventory.reserve(cart.getItems());

        // 5. Create shipment
        Shipment shipment = shipping.schedule(cart.getItems(), customer.getAddress());

        // 6. Notify + audit
        notifier.sendConfirmation(customer, tx, shipment);
        audit.log("ORDER_PLACED", customer.getId(), tx.getId());

        return OrderResult.success(tx, shipment);
    }
}

Composite Treat individual objects and compositions uniformly — Tree Structures

▼

Intent: Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions uniformly via the same interface.

// Use case: File system — files and folders both have size(), name(), list()
// Without Composite: if(isFile) ... else if(isFolder) ... → conditionals everywhere

public interface FileSystemNode {
    String getName();
    long getSize();
    void print(String indent);
}

// Leaf — no children
public class File implements FileSystemNode {
    private final String name;
    private final long size;

    public File(String name, long size) { this.name=name; this.size=size; }
    public String getName()          { return name; }
    public long getSize()             { return size; }
    public void print(String indent)  { System.out.println(indent + "📄 " + name + " (" + size + "B)"); }
}

// Composite — has children, delegates to them
public class Directory implements FileSystemNode {
    private final String name;
    private final List<FileSystemNode> children = new ArrayList<>();

    public Directory(String name) { this.name = name; }
    public void add(FileSystemNode node) { children.add(node); }

    public String getName() { return name; }
    public long getSize() {  // recursive — sums all children (files + subdirs)
        return children.stream().mapToLong(FileSystemNode::getSize).sum();
    }
    public void print(String indent) {
        System.out.println(indent + "📁 " + name + " (" + getSize() + "B)");
        children.forEach(c -> c.print(indent + "  "));
    }
}

Observer Event-driven communication — Push vs Pull models

▼

Intent: Define a one-to-many dependency so when one object changes state, all dependents are notified and updated automatically. Foundation of event-driven architecture.

Observer Pattern: Subject (Observable) ├── subscribe(Observer) ├── unsubscribe(Observer) └── notifyObservers() │ calls update() on each ▼ Observer 1 Observer 2 Observer 3 (all notified on state change)
// Generic Observable with type safety
public interface Observer<T> { void update(T event); }

public class EventBus<T> {
    private final List<Observer<T>> observers = new CopyOnWriteArrayList<>(); // thread-safe

    public void subscribe(Observer<T> o)   { observers.add(o); }
    public void unsubscribe(Observer<T> o) { observers.remove(o); }

    public void publish(T event) {
        observers.forEach(o -> {
            try { o.update(event); }
            catch (Exception e) { /* log but don't stop other observers */ }
        });
    }
}

// Domain event
public record OrderPlacedEvent(String orderId, String customerId, double amount) {}

// Concrete observers — each has its own responsibility
public class EmailNotificationObserver implements Observer<OrderPlacedEvent> {
    public void update(OrderPlacedEvent e) {
        emailService.sendConfirmation(e.customerId(), e.orderId());
    }
}
public class InventoryObserver implements Observer<OrderPlacedEvent> {
    public void update(OrderPlacedEvent e) { inventoryService.reserve(e.orderId()); }
}
public class AnalyticsObserver implements Observer<OrderPlacedEvent> {
    public void update(OrderPlacedEvent e) { analytics.track("order_placed", e.amount()); }
}

// Wiring — OrderService knows nothing about email/inventory/analytics:
EventBus<OrderPlacedEvent> bus = new EventBus<>();
bus.subscribe(new EmailNotificationObserver());
bus.subscribe(new InventoryObserver());
bus.subscribe(new AnalyticsObserver());

// In OrderService.placeOrder():
bus.publish(new OrderPlacedEvent(orderId, customerId, amount));
// All three observers notified — OrderService has zero coupling to them

Chain of Responsibility Pass request along a handler chain until processed

▼

Intent: Avoid coupling sender to receiver by giving multiple objects chance to handle a request. Chain the receivers and pass the request along until one handles it.

public abstract class RequestHandler {
    protected RequestHandler next; // link to next handler

    public RequestHandler setNext(RequestHandler h) { this.next = h; return h; } // fluent chaining

    public abstract Response handle(Request request);

    protected Response passToNext(Request r) {
        return next != null ? next.handle(r) : Response.notHandled();
    }
}

// Handler 1: Authentication
public class AuthHandler extends RequestHandler {
    public Response handle(Request req) {
        if (!req.hasValidToken()) return Response.unauthorized(); // stop chain
        return passToNext(req); // authenticated → pass to next
    }
}
// Handler 2: Rate limiting
public class RateLimitHandler extends RequestHandler {
    public Response handle(Request req) {
        if (rateLimiter.isExceeded(req.getClientId())) return Response.tooManyRequests();
        return passToNext(req);
    }
}
// Handler 3: Business logic
public class BusinessHandler extends RequestHandler {
    public Response handle(Request req) {
        return businessService.process(req); // end of chain
    }
}

// Wire the chain — order matters!
RequestHandler pipeline = new AuthHandler();
pipeline.setNext(new RateLimitHandler())
        .setNext(new BusinessHandler());

Response response = pipeline.handle(incomingRequest);
// Unauthenticated → stops at AuthHandler
// Rate exceeded → stops at RateLimitHandler
// Valid → passes through all three → BusinessHandler responds

Template Method Define the skeleton — subclasses fill in the steps

▼

Intent: Define the skeleton of an algorithm in a base class, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps without changing the algorithm's structure.

Key: The abstract class controls the flow. Subclasses only override the varying steps. Hollywood Principle: "Don't call us, we'll call you."

public abstract class DataProcessor {

    // TEMPLATE METHOD — final: defines the algorithm skeleton, cannot be overridden
    public final void process() {
        Object raw  = readData();      // step 1 (abstract)
        Object clean = parseData(raw);  // step 2 (abstract)
        validateData(clean);            // step 3 (hook — optional override)
        saveData(clean);                // step 4 (abstract)
        onComplete();                    // step 5 (hook — optional override)
    }

    // Abstract steps — MUST be implemented by subclasses
    protected abstract Object readData();
    protected abstract Object parseData(Object raw);
    protected abstract void   saveData(Object data);

    // Hook methods — CAN be overridden, have default implementation
    protected void validateData(Object data) { /* default: no validation */ }
    protected void onComplete() { System.out.println("Processing complete"); }
}

Command Encapsulate requests as objects — undo/redo, queuing

▼

Intent: Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations.

public interface Command {
    void execute();
    void undo();     // reverse the action
}

// Receiver — knows how to do the actual work
public class TextEditor {
    private StringBuilder text = new StringBuilder();
    public void insertAt(int pos, String s) { text.insert(pos, s); }
    public void deleteAt(int pos, int len)  { text.delete(pos, pos+len); }
    public String getText() { return text.toString(); }
}

// Concrete commands — each captures everything needed to execute AND undo
public class InsertCommand implements Command {
    private final TextEditor editor;
    private final int position;
    private final String text;

    public InsertCommand(TextEditor e, int pos, String text) {
        this.editor=e; this.position=pos; this.text=text;
    }
    public void execute() { editor.insertAt(position, text); }
    public void undo()    { editor.deleteAt(position, text.length()); }
}

// Invoker — manages command history for undo/redo
public class CommandHistory {
    private final Deque<Command> history = new ArrayDeque<>();
    private final Deque<Command> redoStack = new ArrayDeque<>();

    public void execute(Command cmd) {
        cmd.execute();
        history.push(cmd);
        redoStack.clear(); // new action clears redo history
    }

    public void undo() {
        if (!history.isEmpty()) {
            Command cmd = history.pop();
            cmd.undo();
            redoStack.push(cmd);
        }
    }

    public void redo() {
        if (!redoStack.isEmpty()) {
            Command cmd = redoStack.pop();
            cmd.execute();
            history.push(cmd);
        }
    }
}

// Usage:
CommandHistory history = new CommandHistory();
history.execute(new InsertCommand(editor, 0, "Hello"));
history.execute(new InsertCommand(editor, 5, " World"));
// editor.getText() → "Hello World"
history.undo();   // removes " World"
history.undo();   // removes "Hello"
history.redo();   // re-inserts "Hello"

State Object changes behaviour when its state changes — finite state machine

▼

Intent: Allow an object to alter its behaviour when its internal state changes. The object will appear to change its class.

When to use over if/else: When a class has multiple behaviours that differ across multiple conditions — the State pattern replaces conditionals with polymorphism.

// Order state machine: PENDING → PAID → SHIPPED → DELIVERED or CANCELLED

public interface OrderState {
    void pay(Order order);
    void ship(Order order);
    void deliver(Order order);
    void cancel(Order order);
    String getStatus();
}

public class PendingState implements OrderState {
    public void pay(Order o) {
        System.out.println("Payment processed");
        o.setState(new PaidState()); // transition
    }
    public void ship(Order o)    { throw new IllegalStateException("Must pay first"); }
    public void deliver(Order o) { throw new IllegalStateException("Must ship first"); }
    public void cancel(Order o)  { o.setState(new CancelledState()); }
    public String getStatus()     { return "PENDING"; }
}
public class PaidState implements OrderState {
    public void pay(Order o)    { throw new IllegalStateException("Already paid"); }
    public void ship(Order o)   { o.setState(new ShippedState()); System.out.println("Shipped!"); }
    public void deliver(Order o){ throw new IllegalStateException("Not shipped yet"); }
    public void cancel(Order o) { o.setState(new CancelledState()); paymentService.refund(); }
    public String getStatus()    { return "PAID"; }
}
// ShippedState, DeliveredState, CancelledState follow same pattern...

public class Order {
    private OrderState state = new PendingState(); // initial state
    void setState(OrderState s) { this.state = s; }

    // Delegates to current state — behaviour changes automatically:
    public void pay()     { state.pay(this); }
    public void ship()    { state.ship(this); }
    public void deliver() { state.deliver(this); }
    public String getStatus() { return state.getStatus(); }
}
// order.pay();   → "PAID" — ship() now valid, pay() throws
// order.ship();  → "SHIPPED" — deliver() now valid
// order.deliver()→ "DELIVERED" — cancel() now throws

Iterator Traverse collections without exposing internal structure

▼

Intent: Provide a way to sequentially access elements of a collection without exposing its underlying representation.

// Custom iterator for a paginated API result — fetches next page lazily
public class PaginatedApiIterator<T> implements Iterator<T> {
    private final ApiClient<T> client;
    private List<T> currentPage = Collections.emptyList();
    private int pageIndex = 0;
    private int itemIndex = 0;
    private String nextPageToken = null;
    private boolean firstFetch = true;

    public boolean hasNext() {
        if (itemIndex < currentPage.size()) return true;
        if (!firstFetch && nextPageToken == null) return false; // no more pages
        fetchNextPage(); // lazy fetch
        return !currentPage.isEmpty();
    }

    public T next() {
        if (!hasNext()) throw new NoSuchElementException();
        return currentPage.get(itemIndex++);
    }

    private void fetchNextPage() {
        PagedResult<T> result = client.fetchPage(nextPageToken);
        currentPage = result.getItems();
        nextPageToken = result.getNextToken(); // null if last page
        itemIndex = 0; firstFetch = false;
    }
}

// Client uses standard for-each — doesn't know about pages or HTTP calls:
for (User user : new PaginatedApiIterator<>(apiClient)) {
    processUser(user);  // transparent lazy pagination
}

Circuit Breaker Pattern

Prevents cascade failures when a downstream service is failing. Like an electrical circuit breaker — trips open to protect the system.

// Files are split into 4MB chunks before upload
// Each chunk identified by SHA-256 hash (content-addressable storage)

public class FileChunker {
    private static final int CHUNK_SIZE = 4 * 1024 * 1024; // 4 MB

    public List<Chunk> chunk(File file) throws Exception {
        List<Chunk> chunks = new ArrayList<>();
        try (FileInputStream fis = new FileInputStream(file)) {
            byte[] buffer = new byte[CHUNK_SIZE];
            int bytesRead;
            int index = 0;
            while ((bytesRead = fis.read(buffer)) != -1) {
                byte[] data = Arrays.copyOf(buffer, bytesRead);
                String hash = sha256(data);
                chunks.add(new Chunk(index++, hash, data));
            }
        }
        return chunks;
    }
}
// Upload: check which chunks already exist (dedup) → only upload new chunks
// Delta sync: compare chunk hashes → only re-upload changed chunks

// Bloom Filter for URL deduplication
public class URLBloomFilter {
    private final BitSet   bits;
    private final int      size;
    private static final int NUM_HASH_FUNCTIONS = 7;

    public URLBloomFilter(int expectedInsertions) {
        // Optimal size: -n*ln(p) / (ln2)^2 where p=0.01 (1% false positive)
        this.size = expectedInsertions * 10;  // ~10 bits per element
        bits = new BitSet(size);
    }

    public void add(String url) {
        for (int i = 0; i < NUM_HASH_FUNCTIONS; i++)
            bits.set(hash(url, i) % size);
    }

    public boolean mightContain(String url) {
        for (int i = 0; i < NUM_HASH_FUNCTIONS; i++)
            if (!bits.get(hash(url, i) % size)) return false;
        return true;   // might be present (false positive possible)
    }
}
// 1B URLs × 10 bits = 10 billion bits = 1.25 GB — fits in memory!

Rate Limiting: Token Bucket Algorithm
// Token Bucket in Redis — O(1), atomic via Lua script
// Each client gets a bucket of N tokens, refilled at R tokens/sec

local key       = "rate:" .. clientId
local capacity  = tonumber(ARGV[1])   -- max tokens (burst size)
local refillRate= tonumber(ARGV[2])   -- tokens per second
local now       = tonumber(ARGV[3])   -- current Unix timestamp (ms)

local bucket = redis.call("HMGET", key, "tokens", "last_refill")
local tokens     = tonumber(bucket[1]) or capacity
local lastRefill = tonumber(bucket[2]) or now

-- Refill tokens based on elapsed time
local elapsed = math.max(0, now - lastRefill)
tokens = math.min(capacity, tokens + elapsed * refillRate / 1000)

if tokens >= 1 then
    redis.call("HMSET", key, "tokens", tokens-1, "last_refill", now)
    return 1  -- ALLOWED
else
    return 0  -- RATE LIMITED → 429 Too Many Requests
end
💡 The Lua script executes atomically in Redis — no race conditions. This is exactly how Cloudflare, Kong, and AWS API Gateway implement rate limiting.

Redis Redlock Algorithm (Martin Kleppmann's critique aside)
// Redlock: acquire lock on N/2+1 Redis nodes independently
// If majority acquired AND total time < TTL → lock is safe

public class RedisDistributedLock {
    private final RedisClient redis;
    private static final long TTL_MS = 30_000; // 30 second lease

    public boolean tryAcquire(String resource, String ownerId) {
        // SET key value NX PX ttl — atomic, only sets if not exists
        String result = redis.set(
            "lock:" + resource, ownerId,
            SetParams.setParams().nx().px(TTL_MS) // NX=only if not exists, PX=ms expiry
        );
        return "OK".equals(result); // null if lock already held
    }

    public boolean release(String resource, String ownerId) {
        // Lua script: compare-and-delete (atomic — prevents releasing another owner's lock)
        String luaScript = 
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "  return redis.call('del', KEYS[1]) " +
            "else return 0 end";
        return (Long) redis.eval(luaScript,
            Collections.singletonList("lock:" + resource),
            Collections.singletonList(ownerId)) == 1L;
    }
}

// Usage pattern:
String lockId = UUID.randomUUID().toString();
if (lock.tryAcquire("booking:room:101:2024-12-25", lockId)) {
    try {
        processBooking(); // only one thread across all servers does this
    } finally {
        lock.release("booking:room:101:2024-12-25", lockId); // always release
    }
} else {
    throw new ConflictException("Room already being booked");
}

        if (cdr.roamingNetwork() != null)

        double tax = taxService.calculate(charge, cdr.msisdn());

        return new RatedRecord(cdr, charge, tax, charge + tax);
    }
